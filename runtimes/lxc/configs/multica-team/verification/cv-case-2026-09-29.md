# Verification — the CV case of 2026-09-29 against the four flow rules

The four rules added to `lab-orchestration` §7.1 and §7.4 were replayed against the one run
that exercises all of them end to end: the CV page on the blog, issues TAZLAB-22 (parent,
Ambrogio) → TAZLAB-24 (stage 1, Blog prototype) → TAZLAB-25 (stage 2, Blog corrections) →
TAZLAB-26 (stage 3, Release publish).

Everything below is read from the live control plane (`multica issue get`,
`multica issue comment list` against workspace `tazlab`), not from what an agent reported
about itself. The comments were fetched after the run.

## Rule 7.4.1 — a question is asked once: **was the question repeated?**

Yes, and the data shows there was nothing to justify the second asking.

- 20:08:55, `ASK:` — *"guarda il prototipo su http://localhost:1313/cv/ e dimmi se l'HTML va
  va bene o se vuoi il PDF al suo posto"*
- 20:32:13, `ASK:` / `WAITING FOR OPERATOR:` — *"approvi il prototipo CV così com'è — pagina
  HTML su `/cv/` con il link al posto del "Blog" — o vuoi il PDF, o delle modifiche?"*

Both ask the same decision, in the same words in substance: HTML as recommended, or the PDF
instead. Between them there were **zero comments from a member** on TAZLAB-22. The only event
was the 20:31:03 system comment announcing that stage 2 had completed — a machine notice, not
an answer. Normalised string similarity between the two asks is 0.455, and the whole of the
difference is the addition of "or changes" to the menu.

**Under the new rule** the 20:32 run would have written one line — *the question asked at
20:08 is still open* — and pointed at the comment that asked it. The operator's first
opportunity to answer would have been the 20:08 comment itself, 24 minutes earlier, and no
round trip would have been spent.

## Rule 7.4.2 — whoever finishes delegates: **did the finisher open the next step?**

No. On TAZLAB-25 the Blog agent had finished its work — `c10cf24` committed, verified,
`hugo --minify` exit 0, both body diffs empty — and wrote at 20:25:43:

> *"**Publishing is not mine.** If you want the CV page live, that is a release issue to the
> **Release** agent — push, deploy, verify on `blog.tazlab.net`. **Say the word and it gets
> opened**; I will not push."

and, on the same page:

> *"**`Kustomize` in the Italian CV** … so it is a Job-agent issue, not this branch.
> **Unopened until you ask.**"*

Both are the failure. The release issue TAZLAB-26 was created at **20:34:26 by Ambrogio**, and
the operator's approval that triggered it is at **20:33:35** — so the chain did not restart
because an agent delegated; it restarted because the **operator** said "vai approvo" and the
orchestrator picked the work up. The test in the new rule — *after the run, does the next step
exist as an issue with an assignee?* — answers **no** for the 20:25:43 run.

**Under the new rule** the same run opens the release issue to Release (with Source / Requested
action / Expected effect / Acceptance / Boundaries) and the Job issue for the `Kustomize`
question, and says in one line that it did. The operator's next message would have been
Release's approval request, not a correction.

## Rule 7.4.3 — an announcement is not a request: **was news put inside `ASK:`?**

Yes. TAZLAB-22, 20:34:57, immediately after the approval:

> `ASK: nothing — il gate è superato, il rilascio è con Release e ti arriva la sua richiesta
> di approvazione sul push`
> `YOUR MOVE: none.`

Every clause after "nothing" is status about the pipeline: the gate is passed, the release sits
with Release, its request will arrive. None of it is a decision the operator is being asked to
make. The operator has to read past *"nothing"* to check that the run is not, in fact,
soft-pedalling a demand — which is exactly the cost the block was introduced to remove.

**Under the new rule** the same three facts are one line of the summary — *TAZLAB-26 opened to
Release; it will ask you for the push* — and the block reads `ASK: nothing` /
`YOUR MOVE: none` with nothing implied.

## Rule 7.1 — the shape of the message: **was the detail longer than the ask?**

Yes, by a wide margin.

| Comment | Length | Where the ask sat |
| --- | --- | --- |
| TAZLAB-22, 20:08:55 | 3 057 chars | after 26 lines of evidence, in a code fence at the bottom |
| TAZLAB-22, 20:32:13 | 3 257 chars | after 31 lines, in a code fence at the bottom |
| TAZLAB-25, 20:10:51 | 2 630 chars | after 36 lines, at the bottom |
| TAZLAB-25, 20:25:43 | 931 chars | at the bottom |

All four are the same shape: a report first, the ask last. The work in question was a few lines
of markdown — `git diff --stat abde2dc` was `content/cv/index.it.md | 4 +---` and
`content/cv/index.md | 2 --` — so none of the four met the ~800-character detail budget, and
in every case the decision the operator was being asked for was the last thing on the page.

**Under the new rule** each is: one line of what changed, the four-line block, then the detail
— files, commands, the two real diffs, what was left undone. The same facts, the ask within
the first six lines.

## What the case does *not* show

The approval gate itself worked. Release armed the wakeup, the issue went to `in_review` and to
the operator, the push happened only after the 20:36:37 approval, and the 20:41:49 verification
brought back real evidence from the live site. The gate is not what these four rules touch, and
nothing here is a reason to change it. What failed was everything *around* the gate: the
question was asked twice, the next step waited on the operator, a status report was dressed as
a request, and the ask was at the bottom of a report four times out of four.
